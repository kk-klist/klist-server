# 협업 컨벤션

klist 팀의 GitHub 협업 규칙이다. 이슈 → 브랜치 → 커밋 → PR → 머지로 이어지는 작업 흐름과 보드 운영 방식을 정의한다.

## 이슈 규칙

이슈는 모든 작업의 시작점이다. 아무리 작은 작업이라도 **작업하려는 레포지토리에서 이슈를 먼저 생성**하고 시작한다.

### 이슈 생성 타이밍

| 상황 | 타이밍 |
|---|---|
| 기능 개발, 예정된 작업 | 주간 회의에서 미리 생성 |
| 버그, 갑작스러운 작업 요청 | 발견 즉시 생성 |
| 나중에 하면 좋을 아이디어 | 떠오를 때 Backlog에 추가 |

### 이슈 제목 규칙

Conventional Commits 스펙을 기반으로 한다.

```
feat: 새로운 기능
fix: 버그 수정
docs: 문서 작업
refactor: 코드 개선
chore: 설정, 패키지 등 기타
```

### 이슈 본문 템플릿

이슈 템플릿은 각 레포가 아니라 조직 공용 레포([kk-klist/.github](https://github.com/kk-klist/.github))의 `.github/ISSUE_TEMPLATE/`에서 관리되며, 이 레포에 별도 템플릿이 없으면 GitHub이 자동으로 가져와 적용한다. 타입에 따라 두 가지를 사용한다.

- **Feature / Task** (`feature.yml`) — feat / docs / refactor / chore 공통. 필드: 작업 타입(드롭다운), 작업 배경, 완료 조건(체크박스), 참고 자료(선택)
- **Bug Report** (`bug.yml`) — fix 전용, 라벨 `fix` 자동 부착. 필드: 문제 상황, 재현 방법, 완료 조건(체크박스), 참고 자료(선택)

이 폼은 브라우저에서만 렌더링되고 필수 필드 검증도 웹에서만 적용되므로, 이슈는 `gh issue create --web`으로 템플릿 선택 화면을 열어 생성한다.

## 라벨 규칙

모든 레포에 아래 라벨셋을 동일한 이름으로 생성한다. Org Project에서 여러 레포 이슈를 필터링/그룹화하는 기준이 되므로, 이름과 표기를 절대 다르게 만들지 않는다.

| 구분 | 라벨 |
|---|---|
| 타입 | `feat`, `fix`, `docs`, `refactor`, `chore` |
| 우선순위 | `priority: high`, `priority: medium`, `priority: low` |
| 기타 | `blocked` (작업이 막혔을 때 부착) |

> 새 레포가 추가되면 이 라벨셋을 그대로 복사해서 생성한다. 레포마다 수동으로 만들면 이름이 미묘하게 달라질 수 있으니, GitHub CLI 스크립트로 일괄 동기화하는 것을 권장한다.

## 브랜치 규칙

```
main          <- 배포용. 직접 push 금지
└── develop   <- 개발 통합 브랜치
    └── feature/이슈번호-작업명
```

### 브랜치 네이밍

```
feature/12-login-api
fix/34-signup-error
```

## 커밋 규칙

Conventional Commits 스펙을 기반으로 하며, 이슈 번호를 함께 포함한다.

```
feat: 로그인 API 연동 (#12)
fix: 회원가입 버튼 클릭 오류 수정 (#34)
docs: README 설치 방법 추가
refactor: AuthService 코드 정리 (#41)
```

## PR 규칙

- `feature` 브랜치에서 PR을 생성하거나 커밋을 푸시하면 즉시 CI가 자동 실행된다.
- `develop` 브랜치로의 머지는 **CI 통과 + 리뷰어 승인 1개 이상**을 모두 만족해야 가능하다.
- `develop` 브랜치에서 `main` 브랜치로의 머지는 배포 담당자가 진행한다.
- 머지 방식은 squash를 사용한다.

### PR 본문 템플릿

이슈 템플릿과 마찬가지로 [kk-klist/.github](https://github.com/kk-klist/.github)의 `.github/pull_request_template.md`에서 조직 공통으로 관리한다. 이 레포에 별도 템플릿 파일을 만들지 않는다.

```markdown
## 작업 내용
-

## 변경 사항
-

## 관련 이슈
Closes #
```

### PR 원칙

- PR 하나는 하나의 목적만 갖는다. 여러 기능을 묶지 않는다.
- 리뷰어를 반드시 1명 이상 지정한다.
- `Closes #번호`는 누락 없이 작성한다. 없으면 머지 후 이슈가 자동으로 닫히지 않는다.
- 승인(Approve) 1개 이상일 때만 머지한다.

## 주간 플로우

```
월요일  Backlog 검토 -> 이번 주 Todo 선정 -> 담당자 배분        (15분)
평일    작업 시작 -> 브랜치 생성 -> 커밋 -> PR -> 리뷰 -> 머지
금요일  완료 이슈 리뷰 -> 지연 이슈 원인 파악 -> 다음 주 조정    (10분)
```

## 보드 상태 업데이트 규칙

보드는 항상 실제 작업 상태를 반영해야 한다.

| 시점 | 해야 할 일 |
|---|---|
| 작업 시작할 때 | 이슈를 In Progress로 이동 |
| PR 올렸을 때 | 이슈를 In Review로 이동 |
| 머지 완료 후 | 이슈 자동 Done (`Closes #` 작성 필수) |
| 작업이 막혔을 때 | 이슈에 코멘트로 상황 공유 |

## 주의사항

- **보드 상태 실시간 유지** — 상태 업데이트가 늦어지면 팀원이 진행 상황을 파악할 수 없다. 상태 변경은 즉시 한다.
- **main 직접 push 금지** — 반드시 PR과 리뷰를 거쳐 머지한다. 브랜치 보호 규칙이 설정되어 있다.
- **PR 크기를 작게 유지** — PR 하나에 너무 많은 변경이 담기면 리뷰가 어렵고 충돌이 늘어난다. 기능 단위로 잘게 나눈다.
- **Backlog 정기 정리** — 2주 이상 방치된 이슈는 주간 회의에서 닫거나 우선순위를 재조정한다.
